# ZERO Security Disclosure Policy

## Reporting

Security researchers should use the designated ZERO security contact published by the project rather than public issue trackers for sensitive vulnerabilities.

Reports should contain enough technical detail to reproduce the issue, while minimizing user data.

Do not include:

- private messages
- private files
- device private keys
- recovery secrets
- passwords or authentication tokens
- unnecessary personal information

If sensitive material is unavoidable, use the approved secure reporting channel and provide the minimum necessary evidence.

## Handling lifecycle

Reports move through:

RECEIVED → TRIAGED → ACKNOWLEDGED → REMEDIATION → RETEST → RESOLVED → CLOSED

Severity is classified as LOW, MEDIUM, HIGH, or CRITICAL.

Confirmed fixes should receive retest evidence before closure where applicable.

## Researcher safety

Good-faith security research should avoid data destruction, service disruption, persistence, credential theft, unnecessary data access, or actions against accounts that do not belong to the researcher.

Researchers should stop testing and report immediately when they encounter unrelated user data.

## Public disclosure

ZERO may publish an advisory after remediation and evidence review. Reporter identity is not published without appropriate permission.

No bounty, reward, or legal safe-harbor promise is implied unless a separate program explicitly establishes it.

## What ZERO will not claim

ZERO will not describe an audit, penetration test, certification, or security control as complete without corresponding retained evidence.
